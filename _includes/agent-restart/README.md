# 重启之后，核对同一份回执

原创AI辅助的Python3.11+标准库练习。Python需带sqlite3；不安装pip包、
模型SDK，不需要API Key。程序只在自己创建的临时目录使用一个SQLite文件，
结束时清理，没有网页、HTTP、用户数据库或私人手记读入接口。

```sh
python3 demo_restart.py
python3 run_checks.py
```

第一条实际创建子进程、执行SQLite事务，在指定位置让子进程用os._exit(75)
退出，再由新进程重开同一个数据库。六行JSON来自实际观察，不是预写回包。
第二条实际运行八项检查；不是模型分数、操作系统断电或所有VFS恢复测试。

## 三个文件

- receiver.py：两张小表与应用/查询函数。counter和receipt在同一数据库、
  同一BEGIN IMMEDIATE事务里更新，COMMIT后才返回普通回执。固定op-1/op-2，
  增量为整数1–3，不执行外部副作用。内部worker入口才安装退出故障。
- demo_restart.py：为每个情景创建全新临时数据库，用参数列表启动自己的
  Python子进程，无shell。记录实际退出码/回执，另起独立观察子进程重开查询。
- run_checks.py：事务前后真实退出、两张表一起回滚、参数冲突、历史快照、
  两个独立子进程同key、文件不覆盖和坏版本/回执不自动修复。

## 先预测，再看输出

| 情景 | 首次观察 | 重开后的实际结果 |
| --- | --- | --- |
| after-commit-retry | 子进程退出75，没有回执；客户端unknown | 数据库值2，原key重发取回旧回执，不再增加 |
| before-commit-retry | 同样退出75，没有回执 | 没有已提交值，再发才实际增加2 |
| after-commit-lookup | 提交后丢回执 | 新进程查询找到原回执，不再次增加 |
| changed-payload | 提交后丢回执 | 同key改为3被拒绝，仍为2 |
| new-key | 提交后丢回执 | op-2增加1是新操作，累计3 |
| historical-receipt | 两次正常提交 | 查op-1的历史值2，数据库当前值3 |

client_trace没有收到回执时response保持null。teaching_observer是拥有
临时数据库的教学视角，读取也实际另起新进程；这些观察进程不计作客户端
动作。真实远端客户端不会自动获得它。两种中断在客户端
都未知，不能只凭退出码判定是否提交。每一步启动新的子进程，不把在一个
对象里重设变量叫重启。两张表读取也在一个读事务里，避免混合两个时点。

## 事务能覆盖的边界

这里把“增加计数”与“保存回执”放在同一SQLite文件事务中。只要它们
属于同一个事务，进程中断后的处理可以依据已提交记录。初始化专门使用
独占新文件创建；找错恢复路径会失败，不偷偷建一份空数据库当成旧状态。
版本或记录不一致会报错，不自动清空/补成功。数据库是本程序自己生成的
小例子，不是导入任意不可信SQLite文件的验证器。

数据库文件、事务、程序上下文、模型消息与学习手记是不同层。网页回执
实验仍只有内存，这份下载练习才有实际文件与进程。它也不是完整Agent。

如果事务之外还要发送邮件、发布内容或调用远端写工具，单个SQLite提交
不会把那些外部效果一起纳入原子事务。此处没有实现事务发件箱、补偿、
分布式事务、缓存过期、账户权限或恢复生产数据的流程。

本例使用rollback journal/DELETE与synchronous=FULL，实际记录运行时SQLite
版本；没有编译最新上游SQLite，也没有进行断电、磁盘故障、网络文件系统
或强制kill的穷尽检查。os._exit跳过Python finally，但进程退出仍不同于
机器掉电。不要把八项程序检查当成跨服务exactly-once或耐久性认证。
