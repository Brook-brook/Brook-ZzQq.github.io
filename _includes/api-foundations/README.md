# 从JSON到一次HTTP：原创标准库练习

Python3.11+，无需pip、API Key、SDK或外部模型。所有数据是原创教学输入，
不是模型输出、校园规则或真实服务的健康记录。先在自己的目录运行：

```sh
python3 demo_json.py
python3 demo_http.py
python3 demo_delivery.py
python3 run_checks.py
```

第一条实际解析四个JSON。第二条启动短时本机HTTP服务并通过真实socket
执行十一个固定GET案例；第三条用真实POST、计数变化和主动断线，对照
六种未知结果/重试/核对情景，最后关闭。服务仅绑定127.0.0.1临时端口，不
提供文件、任意URL或账户接口。浏览器Pyodide只共享JSON核心，不能在
Pages里运行本机HTTP部分；下载或打开.py不会由网站替你执行。

## 文件各管哪一层

- json_contracts.py：2048个UTF8字节上限，拒绝重复键/NaN等扩展；只接受
  schema_version为整数1、task为sum、values为1–8个有限数且各在±1000内。
  布尔、数字字符串、未知字段不会被强制转换。只计算教学加和，不执行工具名。
- json_cases.py与demo_json.py：公开固定输入，结果由实际函数得到，不预写输出。
- http_client.py：固定loopbackGET，单次显式尝试、响应层/正文大小/UTF8/类型
  检查，再走同一JSON核心；不自动重试、不跟随重定向、不读取环境凭据。
- http_fixtures.py与demo_http.py：原创故障情景。HTTP和断开/超时真实发生，
  故障与返回正文由脚本安排，不是访问公开互联网所得。
- run_checks.py：实际边界、独立小和公式和本机HTTP矩阵检查。通过程序检查
  不等于真实任务做对、模型能力、服务认证或生产系统可靠。
- effect_model.py：小整数接收端的纯函数。普通模式重复加和；keyed模式
  在本机内存记住key、精确参数与回执，冲突不再应用。只有op-1/op-2两key。
- delivery_http.py与demo_delivery.py：自己实现的Idempotency-Key契约和
  回执查询，不是给任何远端服务随便加header就能获得的保证。服务把接收
  和缓存记账放进同一进程锁；默认六例仅是课堂案例，不是性能/可靠性成绩。
- MANIFEST.json：明确公开源的哈希；只能帮助比对内容，不是身份认证。

## 先找层次，再决定下一步

valid得到total6；200坏JSON停在json层，200布尔值停在contract层；错媒体
类型停在representation层。204是HTTP成功但没有正文，本应用期望JSON，
不能填一个0。429/503保留Retry-After的原始短值，本客户端不据此重试。
302不会自动跟随；大正文最多读2049字节；断开与阻塞返回传输类别。

timeout参数是阻塞操作的超时，不是整项任务绝对截止。等待案例在服务端
由Event控制，客户端实际超时；结束时释放等待并回收线程。即使本案例
只有读请求，通用系统也不能把超时解释成服务端没有执行。重试写操作
还要检查服务的幂等契约、预算和授权，不能仅凭状态码做决定。

delivery默认先加2再断开。plain重复发送会得到4，keyed相同参数仍是2；
同key改成3得到冲突，换新key则是新操作。查询旧回执可在不再写入的
情况下找回结果，但回执中的value_after是当时的值，不保证是最新总值。
本机观察者知道内存状态，不等于任意客户端都能知道。没有缓存过期、
重启恢复、持久化、外部数据库或跨服务事务，不能据此宣称分布式exactly-once。

这是刻意收窄的教学契约，不是任意JSON Schema验证器或通用HTTP库。
真实服务需要另行设计HTTPS、认证、权限、数据许可、持久化、并发与完整
任务截止。http.server本身不适合作生产服务；不要把它对外公开。

## 自己改一个可观察断言

先把true改为1，再改成"1"，预测哪种被接受。把1e309与NaN比较：前者可被
解析为非有限float后在数值契约拒绝，后者在严格解析策略中拒绝。用空列表、
重复同名键和超出字节上限的文档找出不同失败层。即使数值范围小例子
都跑对，也不能说明外部数据可信或应当执行任何模型提议。
