本笔记由 AI 辅助整理，原理解说、例子和练习独立编写。先学会设计一个
可核对的小应用，再决定是否需要某个框架；这不是模型能力排行榜。

## 先写一个能验收的任务 {#task}

“做一个很聪明的助手”还不是可验收任务。可以先改成：

> 输入两个**目录中已有的地点ID**，输出采用哪种距离模型、计算结果与资料来源；
> 缺少ID时要求补充，不编造步行路线。

这里确定的球面计算适合交给程序。模型可以帮助理解表达，但不应替代可
复算的计算器、来源检查和应用权限。已有的 [GIS 工具实验](../tool-calling-boundaries/)
正好展示其中的工具部分；它没有真正调用模型。

| 部分 | 应用中要决定什么 | 不能靠一句 prompt 解决什么 |
| --- | --- | --- |
| 任务 | 输入、输出、失败/不足时怎么处理 | 模糊的“有用”无法直接验收 |
| 模型 | 版本、模态、接口、预算、适用条件 | 流畅表达不等于事实正确 |
| 程序与工具 | 类型校验、真实计算、超时和权限 | 工具描述不等于访问控制 |
| 数据 | 来源、版本、允许用途、覆盖范围 | 空目录不证明现实不存在 |
| 评测 | 测试集、基线、错误成本、独立检查 | 一次漂亮演示不是可靠性证据 |

## 模型在预测什么 {#model}

LLM 是 Large Language Model（大语言模型）的缩写。聊天产品、模型本身和
提供调用的 API 接口是不同东西：产品还组织会话、工具、数据与界面。

常见自回归文本生成模型根据已提供的序列，对下一个 token 给出分布，再按
解码策略选择输出，逐步生成。训练还可能包含指令微调、偏好优化等步骤；
“下一 token”也不是所有 AI 模型、所有训练任务的完整定义。多模态模型还
能处理图像、音频等输入，不能一概说模型只会接收文字。

某段回答在模型分布下很可能出现，不意味着它在现实中很可能正确。下一个
token 的概率、整段回答是否有证据、概率是否经过校准，是三个不同问题。
没有来源的日期、引文或数字应保留为待核对，而不是按文风判断可信度。

降低 temperature 通常改变采样的随机程度，不会自动补上资料、修正逻辑或
保证每次完全一致。模型版本、服务实现、输入顺序与其他设置也会影响输出。

## Token 不是字数，上下文也不是永久记忆 {#context}

Tokenizer 把输入转换为模型使用的 token ID。一个英文词、一个汉字或一个
emoji 都不保证对应一个 token；切分依赖 tokenizer 和消息格式，不能用固定
“几个字等于一个 token”作为精确计费或容量检查。

一次实际输入可能包含：应用指令、当前问题、历史消息、工具定义、检索片段
和工具回执。输出及部分模型的推理预算还受到接口各自的额度规则约束。
工程上应使用对应版本的计数方式、检查真实 usage，并为输出预留空间；
本文不编造某个通用窗口大小或价格。

上下文太长不只是费用问题：相关证据可能被截断、淹没，或夹带不可信指令。
删历史、摘要历史和检索历史会丢失不同信息，都需要明确规则。把一句话
放进本轮上下文，不代表模型参数已经学会它，也不代表下一次会自动记住。

## Prompt、RAG、微调，改变的是不同地方 {#changes}

| 方法 | 直接改变什么 | 仍要核对什么 |
| --- | --- | --- |
| Prompt / few-shot | 本次输入中的说明和例子 | 是否适配未见输入；示例是否泄露答案 |
| RAG | 按问题检索并提供外部资料 | 检索是否找对、版本是否适用、回答是否忠于证据 |
| 微调 | 按训练流程更新模型参数 | 数据授权、验证划分、成本、泛化与回归 |
| 应用会话存储 | 程序保存的消息或状态 | 保存/删除规则、访问权限和是否送给模型 |

不是所有任务都需要这四种方法。先用简单规则或单次调用建立基线，只有
明确问题需要额外上下文、动作或学习时，再增加复杂度。RAG 也不要求一定
使用向量数据库；关键词检索可以是合适的起点。

## 做一张最小设计卡 {#exercise}

为自己想做的应用写下：一个输入例、一个期待输出、一个缺少信息的例子、
一个拒绝或失败的例子，以及谁来核对。把每步标成程序、模型、工具或人。

自检：“计算两个已知点的球面距离”和“解释为什么它不是步行路线”分别
需要什么？若把模型拿掉，哪些部分依然应该正确运行？
